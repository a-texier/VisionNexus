01

Le flux, étape par étape

  1. Fenêtre catalogue — grille d'apps + Paramètres, toujours visibles côte à côte. Réglages stockés dans %APPDATA%\VisionNexusElectron\settings.json — indépendant de VisionNexus.
  2. Clic sur une app — lance cmd.exe /c cd /d ... && python launcher.py --app <id> ... en local, ou ssh -t <vm> "... python launcher.py --app <id> ..." sur une VM. Exactement la commande que VisionNexus construit. Aucun raccourci, aucune réimplémentation de la logique de lancement elle-même.
  3. Lecture des ports réels — launcher.py annonce toujours ses ports sur sa sortie ([config] backend = http://localhost:XXXX). Ce lanceur les lit en direct, jamais de port supposé à l'avance.
  4. Tunnel (VM uniquement) — une deuxième connexion SSH pure (-N -L) s'ouvre une fois les vrais ports connus.
  5. Attente — sonde http://127.0.0.1:<port> jusqu'à réponse.
  6. Onglet docké — l'app s'ouvre comme un onglet dans la fenêtre catalogue (logo + nom visibles dans la barre, à côté de l'onglet "VisionNexus"), badge "Natif"/"HTTP (repli)" en haut à droite pour les apps compatibles (cf. Chemin natif). Glisser l'onglet hors de la barre le détache dans sa propre fenêtre Windows (avec sa propre icône dans la barre des tâches) — le repos­itionner n'est pas nécessaire, juste le lâcher en dehors suffit.

Fermeture & logs

Fermer un onglet (croix) ou la fenêtre détachée tue les process associés (lancement + tunnel) — l'app distante s'arrête, même mécanique que fermer le terminal de VisionNexus. Chaque lancement écrit un log complet (stdout+stderr bruts, jamais tronqué) dans %APPDATA%\VisionNexusElectron\logs\ — bouton "Logs" dans le catalogue pour ouvrir le dossier directement.

03

Gestion des ports

Confirmé en lisant _lib/launcher_engine.py : les ports sont alloués dynamiquement (find_free_port()), sauf si --backend-port/--frontend-port sont passés explicitement — auquel cas aucune vérification de collision n'est faite.

Conséquence sur la conception

Le catalogue contient des ports par défaut (affichage seulement) — ils ne sont jamais envoyés à launcher.py. Le port réellement utilisé est toujours celui que launcher.py annonce lui-même. Ça permet plusieurs instances en parallèle sans collision, comme pour n'importe quel autre client (terminal manuel, VisionNexus).

04

Electron — principe et pourquoi ce choix

Electron empaquette Chromium (moteur du navigateur) + un runtime Node.js dans un exécutable autonome. Le process main (tout ce qui est dans src/) a accès au système — fichiers, réseau, sous-process. Le process renderer (ce qui s'affiche, le frontend React d'une app) tourne dans une sandbox Chromium standard, sans accès système direct — même posture de sécurité qu'un onglet de navigateur (contextIsolation, sandbox, nodeIntegration: false partout dans ce projet).

Pourquoi pas une réécriture native (Qt/PySide, à la FrameViewer)

Il faudrait soit embarquer QWebEngineView (= encore un Chromium complet, aucune économie), soit réécrire tout le canvas Konva, les stores Zustand, la timeline, les 4 onglets de tracking d'Annotation App en widgets Qt — plusieurs mois, pour un frontend web qui fonctionne déjà.

Pourquoi pas Tauri (Rust)

Les modules à vraie valeur d'ingénierie (découverte de ports, tunnel SSH, protocole image custom avec repli HTTP) sont déjà écrits et fonctionnels en TypeScript. Les réécrire en Rust n'ajoute aucune capacité, juste du travail de traduction, pour un gain de taille de binaire (~10-20 Mo au lieu de ~150 Mo) sans enjeu réel sur un outil interne.

Comparé à "juste du React + Vite"

Un frontend React/Vite classique tourne dans un onglet de navigateur — sandbox complète, aucun accès au système de fichiers, aucune capacité réseau au-delà de ce que le navigateur autorise (HTTP/WebSocket vers le serveur). Electron garde exactement ce même frontend (chargé tel quel via loadURL), mais l'entoure d'un process natif qui, lui, peut :

  • Lire un fichier directement sur un partage réseau monté (SMB ou autre) — impossible pour un onglet de navigateur classique, sandbox oblige.
  • Piloter des sous-process (SSH, tunnels) sans dépendre d'un terminal externe.
  • S'épingler, avoir sa propre icône par app, se comporter comme une app installée — pas un onglet parmi d'autres.

Le frontend React/Vite lui-même ne change pas — c'est la coquille autour qui change ce qu'il est capable de faire.

Et Chromium/HTTP tout seul, sans le chemin fichier natif ?

Une partie du gain est indépendante du chemin fichier natif décrit plus bas — elle vient juste du fait qu'Electron sert le frontend depuis une fenêtre native plutôt qu'un onglet public :

  • La limite de 6 connexions simultanées par origine (HTTP/1.1, imposée par le navigateur) s'applique toujours à Chromium dans Electron — ce n'est pas une sandbox de navigateur qui disparaît, c'est le même moteur de rendu. Un onglet classique et une fenêtre Electron sont logés à la même enseigne sur ce point précis.
  • Le vrai levier disponible sans toucher au backend serait de servir les images en HTTP/2 (multiplexage natif, une seule connexion TCP, des dizaines de flux en parallèle — plus de plafond à 6) si le serveur (uvicorn) et le tunnel le permettent. Non exploité aujourd'hui : uvicorn tourne en HTTP/1.1 simple, et le tunnel SSH ajoute de toute façon une latence par requête que HTTP/2 seul ne supprime pas.
  • C'est précisément pour ça que le chemin natif (section suivante) a plus de valeur ici qu'un simple passage HTTP/2 : il ne contourne pas juste la limite de connexions, il contourne le tunnel SSH lui-même pour les pixels — HTTP/2 seul ne l'aurait pas fait.
05

Empaquetage — comment Node/Electron devient un .exe

electron-builder (déjà en devDependencies) fait trois choses pour produire VisionNexusElectron.exe :

  1. Compile tout src/*.ts en JS (tsc, cf. npm run build) dans dist/.
  2. Empaquette dist/ + ui/ + assets/ dans une archive asar (un seul fichier, lecture rapide, pas modifiable en clic-droit) — voir "files"/"extraResources" dans package.json.
  3. Colle cet asar avec un binaire Electron précompilé pour Windows (Chromium + Node.js déjà liés ensemble par le projet Electron, télécharge une seule fois via devDependencies) — résultat : un seul .exe "portable" (target: "portable" dans package.json), aucune installation, aucun runtime à poser sur la machine cible.

Pourquoi c'est ~150 Mo pour un outil aussi simple

Chromium complet + Node.js sont embarqués dans chaque exe Electron, indépendamment de la taille du code applicatif (quelques centaines de Ko ici). C'est le compromis du choix Electron (cf. section 04) — accepté sciemment, l'outil restant strictement interne.

Rebuild l'exe Windows (copier-coller)

cd Computer_Vision_App\desktop
npm install
npm run dist:win

Sort dans desktop\release\VisionNexusElectron.exe. desktop\release\win-unpacked\ est juste le dossier de build intermédiaire non compressé (peut faire 250+ Mo) — pas un livrable, supprimable sans risque, régénéré à chaque build.

Un exe Linux, avec le même code ?

Oui, sans réécrire la moindre ligne de src/ — electron-builder supporte nativement les cibles Linux (AppImage, .deb, .snap...). La config et le script sont déjà en place :

# A LANCER SUR UNE MACHINE LINUX (ou WSL2) -- cross-compiler depuis
# Windows fonctionne parfois mais est fragile (deps natives, symlinks).
cd Computer_Vision_App/desktop
npm install
npm run dist:linux

Sort un .AppImage dans desktop/release/ — un seul fichier executable (chmod +x puis lancer directement), aucune installation.

Utilité réelle ici

Ce lanceur pilote des commandes locales Windows (cmd.exe) ou SSH vers une VM Linux — sur les deux chemins, la machine qui exécute ce lanceur est aujourd'hui toujours Windows. Un exe Linux n'aurait de sens que si quelqu'un veut lancer ce catalogue depuis un poste Linux (station de dev Linux, autre VM en libre-service...) — la config est prête, mais pas un besoin actuel identifié.

06

Chemin natif (partage réseau) — générique, pas figé à un nom d'hôte

Historiquement, le nom d'hôte du partage réseau n'existait que dans les réglages internes de chaque app (native_share_host, propre à Annotation App, Inference App...) — invisible depuis ce lanceur, aucun moyen de savoir si le partage était joignable avant qu'une app échoue silencieusement dessus.

Paramètres → "Partage réseau natif" centralise ça côté lanceur : un champ générique (n'importe quel nom d'hôte, SMB ou autre protocole de fichiers monté côté Windows), testé à la demande (bouton "Tester") avec un statut joignable / injoignable et la liste des zones (partages) détectées. Rien n'est supposé : champ vide par défaut, aucune app ne tente le chemin natif tant qu'il n'est pas rempli et vérifié joignable.

Mécanique (desktop/src/imageProtocol.ts) — protocole custom app-image://native/?imagePath=...&fallback=..., générique, aucune app en dur dedans :

  1. Le frontend de l'app fournit lui-même les deux urls absolues (il connaît son propre backend) : celle du petit endpoint JSON .../xxx-path et celle de l'endpoint HTTP classique en repli.
  2. Si le partage est marqué joignable : GET sur imagePath (sur le tunnel déjà ouvert, coût négligeable) → {"native_path": "\\\\hote\\partage\\..."} ou null.
  3. Si présent : lecture directe du fichier (fs.readFile), hors tunnel SSH — c'est le gain.
  4. Repli automatique et visible (badge en haut à droite de la fenêtre de l'app : Natif ou HTTP (repli), tooltip avec la raison) dès qu'une étape échoue — jamais d'image cassée, jamais un repli silencieux.

Pourquoi c'est plus rapide quand c'est actif : un navigateur classique est limité à 6 connexions simultanées par origine (HTTP/1.1, cf. section Electron ci-dessus), et chaque requête image passe par le tunnel SSH (latence + bande passante partagée avec tout le reste). Un partage de fichiers n'a pas cette limite façon navigateur, pas de JSON par image, une session authentifiée une fois, lecture quasi directe.

État réel

Le serveur de partage côté VM n'est pas forcément déjà configuré. Le code client suppose un partage déjà accessible (comme celui qu'utilise déjà "Ouvrir dans l'explorateur" de VisionNexus). Si l'hôte configuré ne répond pas, le badge affiche "HTTP (repli)" et tout continue de fonctionner, juste sans le gain de vitesse tant que ce n'est pas en place.

08

Étendre le chemin natif à une autre app

  • Backend de l'app — un endpoint GET .../xxx-path reprenant la logique de résolution de fichier existante, renvoyant {"native_path": to_native_share_path(str(chemin))} (chaque app garde sa propre copie de to_native_share_path — backend/utils/native_share.py — zéro lib partagée entre apps, cohérent avec le reste du dépôt) au lieu de streamer les octets. Le champ native_share_host dans les réglages de l'app doit être configuré avec le nom DNS ou l'adresse du partage.
  • Frontend de l'app — un helper équivalent à nativeImageUrl(httpPath, nativePathEndpoint) (Dataset_Explorer_App/frontend/src/utils/nativeImage.ts) qui bascule vers app-image://native/?imagePath=...&fallback=... quand window.__CV_NATIVE_MOUNT__?.supported est vrai, sinon renvoie l'URL HTTP telle quelle.
  • Ce lanceur — une seule ligne dans desktop/src/catalog.ts : supportsNativeMount: true sur l'AppDef concernée. imageProtocol.ts n'a besoin d'aucun changement : il est déjà générique (les urls viennent du frontend, il ne connaît aucune app par son nom).
